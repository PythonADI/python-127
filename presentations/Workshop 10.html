1. The problem

Without a virtual environment, pip install puts every package into the one Python on your computer. Every project shares that one folder.

Python311/ python.exe Lib/ site-packages/ [hl@2] # shared by every project django/ [closed] django-5.2.18.dist-info/ [closed] pip/ [closed]
projects/ old_shop/ # needs Django 4.2 shop/ [closed] manage.py new_blog/ # needs Django 5.2 blog/ [closed] manage.py

Install Django 4.2 for old_shop…

There is room for only one Django, so pip throws the other one away. Watch site-packages:

@1 $ pip install "django==4.2.*" @1 Installing collected packages: django @1 Attempting uninstall: django @1 Found existing installation: Django 5.2.18 @1 Uninstalling Django-5.2.18: @1 ! Successfully uninstalled Django-5.2.18 @2 Successfully installed django-4.2.30
Python311/ Lib/ site-packages/ django/ [closed gone@1] django-5.2.18.dist-info/ [closed gone@1] django/ [closed new @2] django-4.2.30.dist-info/ [closed new @2] pip/ [closed]

✓ old_shop works.  ✗ new_blog just lost Django 5.2. It is broken.

2. One backpack per project

Each project gets its own .venv folder with its own packages: a virtual environment. Two Djangos, two folders, no fight.

old_shop/ .venv/ [new @1] Lib/ [@1] site-packages/ [@1] django/ [closed @1] django-4.2.30.dist-info/ [closed @1 hl@3] # Django 4.2 shop/ [closed] manage.py pyproject.toml
new_blog/ .venv/ [new @2] Lib/ [@2] site-packages/ [@2] django/ [closed @2] django-5.2.18.dist-info/ [closed @2 hl@3] # Django 5.2 blog/ [closed] manage.py pyproject.toml

It's just a folder

Open .venv and you find a Python and the packages. For one uv add django that's already 4,371 files (34 MB).

On macOS / Linux, Scripts/ is called bin/.

new_blog/ .venv/ Lib/ site-packages/ asgiref/ [closed] django/ [closed hl@2] # Django itself sqlparse/ [closed] tzdata/ [closed] Scripts/ activate django-admin.exe python.exe [hl@1] # this project's Python pyvenv.cfg main.py pyproject.toml

3. uv: one tool for all of it

uv makes the .venv, fills it, and runs your code with it. Five commands.

CommandWhat it does
uv initStart a new project
uv add djangoPut a package in .venv
uv remove djangoTake a package out
uv run python main.pyRun with .venv
uv syncRebuild .venv

uv init: start a project

You get a folder with a few files. No .venv yet: it appears the first time you need it.

@1 $ uv init new_blog @1 Initialized project `new-blog` at `C:\Users\nino\projects\new_blog` @2 $ cd new_blog @2 $
projects/ new_blog/ [new @1] .gitignore [@1] .python-version [@1 hl@2] # which Python main.py [@1] pyproject.toml [@1 hl@2] # settings + package list README.md [@1]

uv add django: install a package

uv creates .venv, downloads Django and the small packages it needs into it, and writes Django down.

@1 $ uv add django @1 Creating virtual environment at: .venv @2 Resolved 6 packages in 281ms @2 Installed 4 packages in 1.74s @2 + asgiref==3.13.0 @2 + django==5.2.18 @2 + sqlparse==0.6.1 @2 + tzdata==2026.6
[project] name = "new-blog" version = "0.1.0" description = "Add your description here" readme = "README.md" requires-python = ">=3.11" dependencies = [ @3 + "django>=5.2.18", ]
new_blog/ .venv/ [dim new @1] Lib/ [dim @1] site-packages/ [dim @2] django/ [closed dim @2] Scripts/ [closed dim @1] .gitignore .python-version main.py pyproject.toml [changed@3] README.md uv.lock [new @3]

uv run: run with the project's .venv

uv run python uses new_blog/.venv. Plain python uses the computer's Python, where Django was never installed.

@1 $ uv run python -c "import django; print(django.__version__)" @1 5.2.18 @2 $ python -c "import django" @2 Traceback (most recent call last): @2 File "<string>", line 1, in <module> @2 ! ModuleNotFoundError: No module named 'django'

Try it — predict the output

old_shop ran uv add "django==4.2.*". new_blog ran uv add django. What prints at each ?

$ cd old_shop $ uv run python -c "import django; print(django.__version__)" ? $ cd ../new_blog $ uv run python -c "import django; print(django.__version__)" ?
→ 4.2.30
→ 5.2.18

Same command, different folder, different .venv. Both versions live on one computer and neither project breaks.

4. Three things in your project

A shopping list, a receipt, and the shopping bag itself.

new_blog/ .venv/ [closed dim hl@3] # bag: the packages .gitignore .python-version main.py pyproject.toml [hl@1] # list: "Django, 5.2 or newer" README.md uv.lock [hl@2] # receipt: exact versions
[[package]] name = "django" version = "5.2.18" dependencies = [ { name = "asgiref" }, { name = "sqlparse" }, { name = "tzdata" }, ] ...

Never commit .venv

It's huge (4,371 files), and it only works on your computer: a Windows .venv doesn't work on a Mac. uv init already hides it from Git.

# Python-generated files __pycache__/ *.py[oc] build/ dist/ wheels/ *.egg-info # Virtual environments .venv [hl@1]
@2 $ git status @2 Untracked files: @2 (use "git add <file>..." to include in what will be committed) @2 .gitignore @2 .python-version @2 README.md @2 main.py @2 pyproject.toml @2 uv.lock @3 # no .venv in the list

5. Sharing a project

Your friend gets the list and the receipt, but no .venv. One command builds exactly the same one.

1 · your laptop
new_blog/ .venv/ [closed dim] # stays here .gitignore main.py pyproject.toml uv.lock
2 · on GitHub
new_blog/ # no .venv .gitignore main.py pyproject.toml uv.lock
3 · friend's laptop
@2 $ git clone https://github.com/nino/new_blog @2 $ cd new_blog @3 $ uv sync @3 Creating virtual environment at: .venv @3 Resolved 6 packages in 1ms @3 Installed 4 packages in 1.51s @3 + asgiref==3.13.0 @3 + django==5.2.18 @3 + sqlparse==0.6.1 @3 + tzdata==2026.6

6. The old way

Before uv: venv + pip. You'll see it in tutorials. Activate means “from now on, python is the .venv one”: watch (.venv) appear in the prompt.

PowerShell: .venv\Scripts\activate
macOS / Linux: source .venv/bin/activate

@1 $ python -m venv .venv @2 $ source .venv/Scripts/activate @3 $ pip install django @3 Successfully installed asgiref-3.13.0 django-5.2.18 sqlparse-0.6.1 tzdata-2026.6 @4 $ pip freeze > requirements.txt @5 $ deactivate @5 $

Old way vs uv

Same jobs. uv is faster and you cannot forget a step.

JobOld wayuv
Createpython -m venv .venvautomatic
Useactivate, then pythonuv run python
Installpip install djangouv add django
Write downpip freeze > requirements.txtautomatic
Rebuildpip install -r requirements.txtuv sync
